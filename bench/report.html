Five Solvers on a Torus

A geometric multigrid V-cycle, used two ways, against Jacobi, SSOR and a sparse direct factorisation — on one discretisation of the surface problem, from 144 unknowns to 589,824. The question is not which is fastest here. It is which one still behaves the same way after refinement.

01 What was measured

Every method solves the same linear system: the same torus, the same cubic finite elements, the same curved mapping. All five agree on the discretisation error to every digit printed, so the comparison is of solvers and nothing else. Each ran in its own container, and the multigrid level hierarchy is built only for the methods that use it — nothing is charged for machinery it does not touch.

The two multigrid rows run through the same prepare_multigrid() and the same V-cycle operator, so they differ in exactly one thing: whether a Krylov space is doing the steering. Everything iterative stops at a relative residual of 10−10.

Two memory numbers, deliberately

Objects counts the matrices, vectors and DoF structures the solver itself holds. Process is the peak resident memory above a measured baseline. The gap between them is memory allocated inside a library — which is where a direct solver's fill-in lives, and where the first number sees nothing at all.

Jacobi does not solve this problem at all

It exhausts its budget of 1000 iterations with the relative residual still at 9.7×10−8 — three orders of magnitude short of what every other method reaches. Its H1 error, 2.570×10−7, is consequently worse than the other four, which agree with each other at 2.549×10−7. It is the only point in the sweep where the methods stop producing the same answer. Its row also looks cheap at 309 s, precisely because it stopped early without solving anything.

The direct solver needs 3.3 GB to factor a 204 MB matrix

A factor of 16.4. Its object memory is unremarkable — the same 203.5 MB Jacobi and SSOR hold, just the active matrix — but the process tells a different story. That gap is fill-in and its internal index arrays, allocated inside UMFPACK. The growth is not academic one level further on: over the last refinement its memory rose by a factor of 4.0 for a factor of 4 in unknowns, so the next size projects past the 8 GB this machine had. 589,824 unknowns is not a stopping point by choice; it is the ceiling.

03 The scaling is the argument

One problem size proves little — a direct solver has a small constant and wins when the problem is small. What matters is how each method responds to refinement. Both charts are log–log; a straight line is a power law, and its slope is the exponent. Hover or tap a chart to read every method at that size.

Because Jacobi's iteration count grows while each iteration costs O(N), its linear algebra grows like N1.26; SSOR is worse at N1.40. Multigrid grows like N0.90. At the largest size that is 62 seconds against 693 — and the gap widens without bound, because these are exponents, not constants.

04 Multigrid as a solver versus as a preconditioner

This is the comparison worth being careful about, and the answer is less dramatic than it is often presented.

Both are mesh-independent — N0.00 and N0.02. So standalone multigrid already delivers the property that made the method famous; it does not need CG to become optimal. What CG adds is a factor of about two: 15 applications of the V-cycle where plain defect correction needs 31, and that ratio holds at every problem size in the sweep.

That is the expected result. Defect correction is a fixed-point iteration, converging at the rate ρ of the V-cycle; CG minimises over a growing Krylov subspace and converges at a rate governed by √κ instead. CG also guarantees monotone decrease of the energy-norm error, which a bare V-cycle iteration does not, and it degrades gracefully if the smoother or the coarse solve is imperfect.

So, is it worth comparing them?

Yes — and the honest summary is CG + MG is about twice as fast, not asymptotically better. A study that reports only one of the two is leaving out exactly this relationship.

05 What these numbers are not

Timings came from emulated hardware

The only available deal.II build was an arm64 image running under emulation on an x86_64 host. Iteration counts, residuals, discretisation errors and byte-level memory are exact and architecture-independent. The wall-clock seconds are not. The exponents are ratios and largely survive the distortion, but absolute times should not be quoted from this run; a native build would be needed for numbers fit for publication.

  • Jacobi's row is a failure, not a data point. Its H1 error differs from the other four, so it should never be presented as “same solution, faster”.
  • Assembly is excluded from the time columns but not from the totals. At the largest size assembly dominates — 162 s of multigrid's 330 s total — so total-time gaps understate the solver-time gaps.
  • One operator, one discretisation. A variable coefficient κ(ξ,η) = 1.1 + sin2ξ cos2η, smooth and bounded away from zero. Multigrid's advantage is sensitive to that; a jumping coefficient would need a different smoother.
